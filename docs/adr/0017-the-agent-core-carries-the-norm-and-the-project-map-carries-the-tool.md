# The agent core carries the norm and the Project map carries the tool

The Testing Policy binds projects in TypeScript, in Python and in Maestro, and its `unit-test-author`
core is regenerated byte for byte in every one of them, so a rule naming a TypeScript package cannot
live there: `render-agent.sh` substitutes only `{{VERSION}}` and has no per-stack block mechanism,
unlike `render-policy.sh`, whose tagged blocks select by surface. A stack-specific tool therefore
splits in two. The core states the norm in stack-agnostic terms, that a fake is never built by
asserting a type at the compiler, and points at the Project map for the helper that replaces the
assertion; the map, preserved per project and filled from what exists there, names the concrete tool
(`fromPartial` and `fromAny` from `@total-typescript/shoehorn`) or records its absence in the form
the map already uses for a missing home, `none yet → <command>` and `n/a`. The label is always
present, since `map_missing` fails an installed agent that lacks a label the template carries, and
the existing `agent_unit_map_missing` path is what fills it on refresh. This is the shape any later
stack-specific tooling in this skill follows.

## Considered options

- Put the whole rule in the core and teach `render-agent.sh` the per-stack tagged blocks that
  `render-policy.sh` has for surfaces: verifiable byte for byte, but it invents a second conditional
  mechanism and writes `as` and `fromPartial` into the agent of a Python repository.
- Put the whole rule in the Project map: no new mechanism, but a normative rule would sit in the
  preserved zone, where a hand edit removes it silently and `verify-policy.sh`, which compares only
  the core, cannot catch it.
